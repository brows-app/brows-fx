## Findings

### #1 [P2] A throwing ready callback leaves the resolver attached after startup fails

- **Status** Deferred. When a ready callback throws, `ImportAgent.Init` has already set `Ready` and the import task has completed (`source/Brows.Composition/Composition/ImportAgents/ImportAgent.cs:100-121`). The composition therefore stays in service through `Imports.Current`: its exports remain usable and may need their private dependencies, and `Kill` still releases the resolver. Whether a callback failure should tear down the imports is a separate decision about existing `Imports.Init` behavior.
- **Location** `source/Brows.Composition/ImportCollection.cs:179-190`.
- **Problem and trigger** The cleanup guard covers initialization and population. Once `ImportState.Ready` returns the collection, `ImportAgent.Init` still invokes queued callbacks and callbacks marked with `[ImportsReadyCallback]`. A callback exception escapes `Imports.Init` after the collection has been cached, leaving its resolver installed.
- **Impact** A failed startup keeps serving later assembly requests from the failed composition's private directories. A subsequent request can load and retain a dependency from that composition for the rest of the process.
- **Evidence** A temporary host queued a throwing callback through `Imports.Changed` and `Imports.Current.ReadyCallback`. On both `net48` and `net10.0`, it caught the callback exception from `Imports.Init`, then successfully loaded the previously unloaded fixture library by name from the private directory. The callbacks run at `source/Brows.Composition/Composition/ImportAgents/ImportAgent.cs:100-125`. The baseline could also propagate callback exceptions, but it registered no dependency resolver.
- **Suggested resolution** Cover the entire startup sequence with cleanup of the agent's acquired collection. Preserve the callback exception and release the resolver if either callback phase fails.
- **Verification** Extend the isolated host cases with a throwing ready callback. After `Imports.Init` faults, a name load of a previously unused private fixture assembly should fail.

### #2 [P2] Killing a pending composition leaves its resolver active until initialization finishes

- **Status** Deferred. The finding is accurate. The resolver, catalogs and containers are released only when the pending initialization settles. Brows kills its imports only after `Imports.Init` completes. A cheap partial remedy is for `ImportState` to cancel the pending initialization from `Dispose` through a linked token, so that cooperative exports stop and the existing cleanup runs at once.
- **Location** `source/Brows.Composition/Composition/ImportAgents/ImportState.cs:53-64` and `source/Brows.Composition/Composition/ImportAgents/ImportState.cs:118-134`.
- **Problem and trigger** The resolver attaches during collection creation. When `IImport.Kill` runs while an export is awaiting work in `IExportAndInit.Init`, the collection cache is still empty. Disposal only sets the flag. Resolver cleanup is deferred until the task settles, and `Kill` does not cancel the pending initialization.
- **Impact** Even after the agent has removed the composition from service, its process-wide handler continues serving new requests. If initialization is blocked indefinitely, the handler can stay attached indefinitely.
- **Evidence** In an isolated process on each of `net48` and `net10.0`, a gated injected export signaled that its initialization had started. After `Imports.Current.Kill()` returned and before the gate was released, `Assembly.Load` successfully bound a previously unused private fixture assembly. After release, the initialization task faulted with `ObjectDisposedException`. The checked-in `ImportStateTest.Dispose_WhileReadyInFlight_KillsAndDisposesOnce` checks disposal only after it releases the gate.
- **Suggested resolution** Give the state ownership of the resolver as soon as composition attaches it, and coordinate detachment with `Kill`, including attachment that races with shutdown. Export cleanup can still wait for the in-flight work to stop using the collection.
- **Verification** Hold initialization at a gate, call `Kill`, and verify that a previously unused private library fails to load before releasing the gate. Then verify that completion reports disposal and cleans up once.

### #3 [P2] A clean standalone test build misses the .NET Framework fixtures [Resolved]

- **Status** Resolved.
- **Location** `tests/Brows.Composition.Tests/Brows.Composition.Tests.csproj:12-18`.
- **Problem and trigger** The component project references are active in the `net10.0` inner build. A clean build of the test project forwards that target framework to the references, so the component build emits only `net10.0` binaries. The `net10.0` test assembly also runs the `net48` integration fixture and attempts to stage its binaries.
- **Impact** A direct project test run fails seven cases before the loader is exercised. A previous solution build can hide the defect by leaving the missing files in `out/components`.
- **Evidence** The standalone Release build in a fresh archive of the target created only `release_net10.0` component outputs. Running the built suite reported 441 passed and seven failed. All failures came from the missing `release_net48` export DLL in `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolutionTest.cs:58-63`. Building the solution produced both fixture targets, after which all 448 tests passed.
- **Suggested resolution** Make the test project's fixture build produce both target frameworks when invoked directly. Remove the caller's target framework from the component build request or explicitly schedule both component targets.
- **Verification** Run the test project directly from an empty output directory. All seven .NET Framework host cases should stage and execute, along with the seven .NET host cases.
- **Resolution** The six component references in `tests/Brows.Composition.Tests/Brows.Composition.Tests.csproj:14-19` now carry `GlobalPropertiesToRemove="TargetFramework"`. With `SkipGetTargetFrameworkProperties="true"` the referencing inner build otherwise passed its own `TargetFramework`, so only `net10.0` was built. Without it, each component's outer build produces every target framework.
- **Fix verification** Before the fix, at `a707c29`, deleting `out/components/bin/*/release_*` and running `dotnet test tests/Brows.Composition.Tests/Brows.Composition.Tests.csproj -c Release` from the repository root produced only `release_net10.0` component outputs. It reported 441 passed and 7 failed: all seven `ComposedDependencyResolutionTest` cases on the `net48` host. After the fix, the same commands produced `release_net10.0` and `release_net48` for all six components. All 448 tests passed (110 on `net462`, 110 on `net48`, 107 on `net8.0`, 121 on `net10.0`). The CI sequence (`dotnet restore`, `dotnet build --no-restore -c Release`, `dotnet test --no-restore -c Release --no-build`) built with no warnings, and every test project reported the same results as before the fix.

### #4 [P3] The new tests assume Windows for plain .NET targets

- **Status** Deferred. The finding is accurate for non-Windows runs. CI runs only on `windows-latest`, and some existing tests (`Brows.CLI.About.Tests`, `Brows.IPC.Host.Tests`) also assume Windows.
- **Location** `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolutionTest.cs:16-17` and `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolutionTest.cs:74-78`. The unit fixture also uses backslashes in paths, for example at `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolverTest.cs:78-84`.
- **Problem and trigger** On Linux or macOS, the integration fixture registers the Framework cases and looks up a Windows `.exe` for the modern .NET host. The resolver unit fixture also passes strings such as `P\Dep.dll` to `Path.Combine`, which creates a filename with a literal backslash on Unix instead of staging a DLL inside `P`.
- **Impact** Contributors running the portable target frameworks can get fixture launch or staging failures unrelated to resolution. The Windows CI matrix does not exercise these cases.
- **Evidence** Static trace of the two fixtures. The .NET SDK uses platform-specific apphost filenames and supports launching the framework-dependent DLL with `dotnet`. [Microsoft .NET deployment documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/#launch-framework-dependent-apps)
- **Suggested resolution** Use platform-aware path construction and launch the modern host via `dotnet` with its DLL. Limit the .NET Framework scenario to Windows.
- **Verification** Run the composition project targeting `net10.0` on Linux and Windows. The modern host cases and resolver unit tests should run on both. Windows should also run the Framework host cases.

### #5 [P3] Committed CRLF blobs defeat the new normalization rules [Resolved]

- **Status** Resolved in the index; the renormalization is staged and becomes part of the branch when committed.
- **Location** `.gitattributes:18-20`. One affected blob starts at `.agents/skills/brows-code-building/SKILL.md:1`.
- **Problem and trigger** The branch introduces LF storage and CRLF checkout rules for Markdown and YAML, after introducing 19 text blobs that still contain CRLF in the index.
- **Impact** The standard branch whitespace check flags 2,058 added lines, obscuring actual whitespace defects. Future edits can also introduce whole-file normalization diffs.
- **Evidence** `git ls-files --eol` shows `i/crlf` alongside `attr/text eol=crlf` for the affected files. The standard branch `git diff --check` flags their carriage returns. It passes when rerun with `core.whitespace=cr-at-eol`, and the code and build-file diff passes without that override.
- **Suggested resolution** Renormalize the affected tracked files with the committed attributes and keep the configured CRLF working-tree endings.
- **Verification** Confirm the affected files show `i/lf` and run the standard merge-base-to-target whitespace check again.
- **Resolution** Ran `git add --renormalize` on exactly the 19 tracked files that `git ls-files --eol` reported as `i/crlf`: the skill files under `.agents/skills/` and `.claude/skills/`, and `agents/plans/2026-11-26_Plan-export-dependency-resolution.md`. Their working-tree copies keep CRLF, as the attributes require. No other text blob was stored with CRLF.
- **Fix verification** `git ls-files --eol` now reports 338 `i/lf` and 2 `i/none` entries, with no `i/crlf` or `i/mixed`. The staged diff changes 2,058 lines in those 19 files, and `git diff --cached --ignore-cr-at-eol` is empty, so only line endings changed. `git diff --cached --check 63eef14` (the merge base against the index) passes without a `core.whitespace` override.
