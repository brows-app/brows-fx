## Findings

### #1 [P2] Release the resolver when a ready callback aborts startup

- **Status** Deferred again. The current implementation keeps the initialized imports available through `Imports.Current` after a callback throws. Changing that behavior requires a decision about whether callback failures abort startup or leave an operational composition. The code is unchanged since the earlier review: `2371366` changed only the test project file and line endings. After a callback throws, the composition is initialized, reports ready and serves its exports, which may need their private dependencies. Detaching only the resolver would therefore break a live composition. A change is warranted only if callback failures are made to roll back the whole startup.
- **Location** `source/Brows.Composition/ImportCollection.cs:179-191`.
- **Problem and trigger** Cleanup catches errors during export initialization and population. A callback registered through `ReadyCallback` or marked with `ImportsReadyCallback` runs after the collection is cached. When the callback throws, the exception escapes the public `Imports.Init` call while the process-wide resolver remains installed.
- **Impact** Code that catches the startup exception can still load previously unused assemblies from that composition. An explicit `Imports.Current.Kill()` is required to release the handler.
- **Evidence** Current source places both callback dispatches after `await ImportTask` at `source/Brows.Composition/Composition/ImportAgents/ImportAgent.cs:100-122`. The application-level acceptance criteria require a failed composition to leave no resolver attached. The earlier isolated hosts observed the retained handler on both `net48` and `net10.0`. The resolver and callback paths are identical at the current target. [Acceptance criteria](../plans/2026-11-26_Plan-export-dependency-resolution.md) · [Earlier runtime evidence](2026-11-26_Review-001.md)
- **Suggested resolution** If callback exceptions continue to fault startup, make startup rollback own the collection through both callback stages and preserve the callback exception during cleanup.
- **Verification** Make a ready callback throw in the component host. After `Imports.Init` faults, loading a previously unused private fixture by name should fail.

### #2 [P2] Detach the resolver when an initializing composition is killed

- **Status** Deferred again. The current Brows host calls `Kill` after initialization. The finding is accurate and unchanged: cleanup is delayed until the pending initialization settles, not lost. The cheap partial remedy recorded in the earlier review still applies: cancel the pending initialization from `ImportState.Dispose` through a linked token.
- **Location** `source/Brows.Composition/Composition/ImportAgents/ImportState.cs:53-64` and `:118-134`.
- **Problem and trigger** If a caller invokes `Imports.Current.Kill()` while an export awaits work in `IExportAndInit.Init`, the resolver has already attached and `CollectionCache` is still empty. Disposal sets `Disposed`, and resolver cleanup waits for the initialization task to settle.
- **Impact** After `Kill` returns, new assembly requests can continue loading private dependencies from the killed composition. A blocked initializer can keep the handler installed indefinitely.
- **Evidence** The factory attaches before composition at `source/Brows.Composition/Composition/ImportCollections/ComposedImportCollectionFactory.cs:87-98`. `ImportAgent.Kill` clears the state and calls `Dispose` at `source/Brows.Composition/Composition/ImportAgents/ImportAgent.cs:210-226`. The earlier gated hosts loaded a previously unused fixture between `Kill` and gate release on both `net48` and `net10.0`. The current source preserves that ordering, and the checked-in test asserts cleanup after opening its gate. [Earlier runtime evidence](2026-11-26_Review-001.md)
- **Suggested resolution** Coordinate ownership of the resolver with `Kill` as soon as it attaches, including an attachment that races with shutdown. Export and container cleanup can run once the pending work settles.
- **Verification** Hold an initializer at a gate and call `Kill`. A previously unused private library should fail to load before the gate opens, and eventual export and resource cleanup should run once.

### #3 [P3] Make modern .NET fixture staging and launch portable

- **Status** Deferred again. The repository CI runs on Windows. The finding is accurate for non-Windows runs. `Brows.CLI.About.Tests` and `Brows.IPC.Host.Tests` also assume Windows.
- **Location** `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolutionTest.cs:16-17` and `:73-78`, and `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolverTest.cs:78-84`.
- **Problem and trigger** On Linux or macOS, the integration fixture registers `net48` host cases and looks for a Windows `.exe` for its modern .NET host. The unit fixture passes paths such as `P\Dep.dll` to `Path.Combine`, so on Unix it creates a filename containing a backslash instead of placing a file in the dependency directory.
- **Impact** Contributors running the modern .NET targets on Unix encounter staging, launch, or resolver assertion failures.
- **Evidence** Source inspection establishes both path flows. The .NET CLI supports launching a framework-dependent host DLL on each platform. Unix execution was unavailable on the Windows review machine. [Framework-dependent deployment documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/#launch-framework-dependent-apps)
- **Suggested resolution** Build dependency fixture paths from separate segments, launch the modern host DLL with `dotnet`, and limit the Framework host cases to Windows.
- **Verification** Run the modern .NET unit and component cases on Windows and Linux. The Framework host cases should continue to run on Windows.

### #4 [P3] Locate component fixtures under the configured artifacts directory

- **Status** Deferred. The finding is confirmed. `tests/components/Directory.Build.props` sets `ArtifactsPath`, but `--artifacts-path` supplies a global property that overrides it. Evaluating `OutputPath` for `Brows.Composition.Component.Export` (`net10.0`, Release) gave `out\components\bin\Brows.Composition.Component.Export\release_net10.0\` by default. With `-p:ArtifactsPath=<custom>` it gave `<custom>\bin\Brows.Composition.Component.Export\release_net10.0\`. The test assembly still embeds `out\components\bin`. Neither CI nor the build skill uses `--artifacts-path`, so the priority is low. A contained fix is a target in `tests/Brows.Composition.Tests/Brows.Composition.Tests.csproj` that runs before assembly attributes are generated. It would call `GetTargetPath` on each component for `net48` and `net10.0`, and embed one `AssemblyMetadata` entry per component and framework for `ComposedDependencyResolutionTest.Output` to read.
- **Location** `tests/Brows.Composition.Tests/Brows.Composition.Tests.csproj:20-23`.
- **Problem and trigger** A build with the SDK's `--artifacts-path` option redirects the component outputs, but the test assembly still embeds the repository's default `out/components/bin` directory. `Output` and `Stage` in `tests/Brows.Composition.Tests/Composition/ImportCollections/ComposedDependencyResolutionTest.cs:54-63` use that embedded path.
- **Impact** On a clean checkout, all 14 integration cases fail before running a host. If the default directory holds binaries from a previous build, the same lookup can select stale fixtures.
- **Evidence** A clean standalone Release build with `--artifacts-path custom-artifacts` emitted the `net48` and `net10.0` fixtures under `custom-artifacts/bin`. There was no `out/components/bin`. A focused run using the same artifacts option reported 0 passed, 14 failed, and 0 skipped. Every failure was a `DirectoryNotFoundException` during the first fixture copy. [SDK test options](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test-vstest)
- **Suggested resolution** Pass the evaluated component output paths to the test assembly or stage the component outputs as part of the test build. Use paths that follow the effective MSBuild output properties.
- **Verification** Run the 14 integration cases from clean default and custom artifacts directories. Both runs should stage fixtures built by the current invocation.
